## 五、门禁和预筛的实际表现

### 大小预筛确实在省时间

18:48 那次，**20+ 个候选在十几秒内被跳过**，一个字节都没下载。20:48 那次同样。

### 但它在边界附近没有分辨力

```
校验 09-16 17:00Z (1155 MB)  →  拒绝
校验 09-16 16:00Z (1180 MB)  →  接受
```

**只差 25 MB。** 所以预筛只能筛掉明显截断的（4 MB、238 MB、416 MB 这类），边界附近必须靠内容门禁。这与设计一致：**预筛只能跳过，不能接受。**

### 自适应阈值在工作

| 运行 | 参考文件 | 大小 | 阈值（×0.75）|
|---|---|---:|---:|
| 18:48-22:48 | 09-15 13:00Z | 1368 MB | 1026 MB |
| 00:48 | 09-16 16:00Z | ~1180 MB | **885 MB** |

发布新数据后，参考文件自动切换成新的线上文件，阈值随之下降。

**这也暴露了一个之前的误判**：我以为健康文件稳定在 1313-1418 MB，但 09-16 16:00Z 只有约 1180 MB 且完全健康。**固定阈值会出错，相对阈值是必须的。**

### 门禁在持续挡住坏数据

00:48 那次：`共 6 个候选，其中 5 个不完整/不可用`。18:48 和 20:48 也各有 2 个被内容拒绝。

NASA 那两天（09-15 15:00Z 到 09-16 16:00Z）产出的文件几乎全是坏的，管线**一次都没发布过坏数据**，只是安静地保留上一版，直到 22:48 拿到健康的 16:00Z。

## 七、观察到的问题与风险

### 1. 单次耗时波动很大（43s - 185s），来源是 NASA 的网络

同一条中止路径，18:48 花了 185s，00:48 只花 43s。日志里能看到单次 HEAD 耗时在 1-23 秒之间跳。

**这不是管线的问题**，但意味着 `replica-timeout 1800` 的余量要留着 —— 如果某个时候 NASA 变得极慢，30 分钟可能不够。（优化前 484s，还有 3.7 倍余量。）

### 2. 发布有约 7 小时的固有延迟

22:48 发布了 **09-16 16:00Z**，即数据名义时刻之后 **6.8 小时**。

原因：NASA 会持续重写文件长达 8 小时，在写完之前门禁会正确拒绝它。**这是设计取舍**：要么等文件写完拿新数据，要么发布可能不完整的数据。选了前者。

想改善只能靠压缩 NASA 的重写窗口（做不到），或者接受发布更旧但确定的文件。

### 3. Log Analytics 是唯一可能产生意外费用的地方

当前日志量小，但容器日志会持续进工作区。**建议设每日上限**（见部署指南第 12 节）。

### 4. 镜像 696 MB，每次执行都要拉取

本次执行启动只花了 2-13 秒（节点有缓存），所以目前不是问题。但如果 Container Apps 回收节点，冷启动会拉 696 MB（压缩后约 200 MB）。

## 八、建议

| 优先级 | 建议 | 理由 |
|---|---|---|
| 高 | **给 Log Analytics 设每日上限** | 唯一的意外账单来源 |
| 高 | **设 Azure Monitor 告警**（任务连续失败）| 现在没人盯着定时任务；失败是静默的 |
| 中 | 试着把 `GCC_SIZE_FILTER_RATIO` 从 0.75 提到 0.85 | 能跳过 1139/1155 MB 这类边界候选，每次省 17-69s；安全阀兜底 |
| 低 | 观察一两周后决定 cron 是否保持 2 小时 | 目前 46% 额度占用，有空间 |
| 低 | 改 App 的 `DataUrls.java` 指向新地址 | 目前 App 还在读 GitHub Pages |

### 关于告警（当前缺口）

现在的失败是**静默的** —— 没有任何通知。虽然 v3 之后没失败过，但"NASA 挂了""镜像拉取失败""发布令牌过期"这类问题不会有任何人知道。

最小可用方案：

```bash
# 任务连续失败时发邮件
az monitor action-group create -n polar-alerts -g "$RG" \
  --short-name polar --email-receiver name=me email=你的邮箱

az monitor metrics alert create -n polar-job-failed -g "$RG" \
  --scopes "$(az containerapp job show -n "$JOB" -g "$RG" --query id -o tsv)" \
  --condition "count JobExecutionFailed > 0" \
  --window-size 1h --evaluation-frequency 15m \
  --action "$(az monitor action-group show -n polar-alerts -g "$RG" --query id -o tsv)"
```

> 具体的指标名（`JobExecutionFailed` 之类）需要以门户里该任务可用的指标为准。

## 九、结论

**迁移目标达成**：

1. **定时可靠** —— 4/4 准点，对比 GitHub Actions 的约 40% 触发率
2. **没有发布过坏数据** —— NASA 连续两天产出损坏文件期间，门禁一次都没放行
