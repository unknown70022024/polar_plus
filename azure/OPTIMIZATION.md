### 安全阀触发条件的修正（重要）

第一版实现的条件是"跳过过任何候选且没找到"就重跑，结果在 2026-09-16 17:30 那次**误触发**——预筛跳过的 7 个是正确的，剩下 2 个因内容被拒，但代码仍完整重跑了一遍，白白多花一倍时间。

改成 **"预筛把存在的候选全部跳过了"** 才触发。区分这两种情况只需要统计"成功 HEAD 到的候选数"：

```python
if chosen is None and skipped and len(skipped) == n_existing:
```

- 预筛跳过 7 / 存在 9 → 不触发（门禁在工作，预筛只是省时间）
- 预筛跳过 9 / 存在 9 → 触发（阈值很可能过时了）

四个场景的验证：

| 场景 | 跳过 | 读取 | 安全阀 |
|---|---:|---:|---|
| A 正常 | 7/9 | 2 | 不触发，选中 |
| B 首次运行（无参考）| 0 | 9 | 不触发，选中 |
| C 阈值过时（比例 2.0）| 9/9 | 9 | **触发，救回并选中** |
| D 真实情况（跳过对+其余全坏）| 7/9 | 2 | 不触发（扫描 26 而非 52）|

> 顺带发现：测试时单次 HEAD 花了 **11.6 秒**（NASA 当时很慢）。所以省掉一次 HEAD 的价值比原计划估计的更高 —— 计划里按 1.3s 估的。

## 二、根本原因：延迟受限，不是带宽受限

**一个 4 MB 的文件花了 31 秒。** 整个文件比一次 8 MB 块还小 —— 拉一次就全在缓存里了。所以那 31 秒不可能花在传输量上。

它花在：

| 开销 | 每次候选 |
|---|---|
| `_wait_stable` 固定睡眠 | **8 秒**（`interval` 默认 8）|
| HEAD 请求 | 3-4 次（搜索循环 1 次 + `_wait_stable` 2 次 + 收尾 1 次）|
| h5py 打开文件 + 元数据 | 若干次分散读，每次一个往返 |
| 读 band 0 | 4 个 chunk = 4 次往返 |

10 个候选 × 8 秒 = **80 秒纯睡眠**，占全程 17%。而 NASA 单次请求往返约 1-1.5 秒，几十次往返累积起来就是另外那 250 秒。

**结论：要提速，重点是减少请求次数和固定等待，不是减少下载量。**

## 三、优化清单（按性价比排序）

### P0 — `_wait_stable` 的 8 秒固定睡眠

**收益：约 -75 秒（16%）｜风险：低**

```python
def _wait_stable(url, max_wait=180, interval=8):   # ← interval=8
    prev = _head_gcc(url)
    while time.time() < deadline:
        time.sleep(interval)                        # 每个候选睡 8 秒
```

这个探测的意义是：NASA 会把文件原地重写（补迟到的高轨颗粒），读到写一半的文件会产生损坏的 chunk。所以要等文件"稳定"。

**但它对老文件是纯浪费。** NASA 实测最多在发布后 8 小时内重写（`Last-Modified` 最多 +8h）。超过这个时间的文件不可能再变。

本次 10 个候选里，7 个超过 10 小时：

| 候选 | 数据龄 |
|---|---|
| 15:00Z / 14:00Z | 2-3h ← 需要探测 |
| 12:00Z | 5h ← 需要探测 |
| 03:00Z | 14h |
| 00:00Z | 17h |
| 23:00Z | 18h |
| 16:00Z | 25h |
| 15:00Z | 26h |
| 14:00Z | 27h |
| 13:00Z | 28h |

改法：
1. **数据龄 > 10 小时的候选直接跳过探测**（省 7 × 8 = 56 秒）
2. 其余的把 `interval` 从 8 秒降到 **2 秒**（省 3 × 6 = 18 秒）

内容门禁本来就会拒绝写一半的文件，稳定性探测是第二道保险，不是唯一防线。

### P0' — 直接删除稳定性探测（最终采用）

P0 先把探测的代价压下去了（老文件跳过 + 间隔 8s→2s），但更彻底的做法是**把它整个删掉**：

```python
# 删除前：每个候选先睡 interval，再比对两次 HEAD
before = _wait_stable(url, max_wait=HEALTH_STABLE_WAIT, age_hours=age_h)
bt, cp, ... = _read_candidate(url, enforce=enforce)
after = _head_gcc(url)
if after == before: return ...

# 删除后：直接用调用方已经拿到的 HEAD 签名
before = before_sig if (attempt == 0 and before_sig is not None) else _head_gcc(url)
bt, cp, ... = _read_candidate(url, enforce=enforce)
after = _head_gcc(url)
if after == before: return ...
```

**为什么可以删**：真正的正确性保证从来不是"等待稳定"，而是 **读取前后两次 HEAD 签名的比对** —— 签名变了就丢弃这次读取并重试。这套机制完整保留。

写一半的文件会以三种方式之一暴露，都不需要预先等待：

1. 数据还没写入 → band 全是 `_FillValue` → **完整性门禁拒绝**
2. chunk 只写了一半 → gzip 解压报错 → **异常 → 重试**
3. 读取期间文件被改写 → 前后签名不一致 → **丢弃重试**

`_wait_stable` 只是在读之前**提前**发现第 3 种情况，代价是每个候选多一次 HEAD 加一段固定睡眠。

**顺带多省一次 HEAD**：搜索循环本来就要 HEAD 一次拿 `Content-Length` 做大小预筛，现在把那个签名直接传给 `read_gcc_bt` 当 `before`。所以每个成功读取的候选少一次往返。

重试时**不复用**旧签名，而是重新 HEAD —— 重试的前提就是文件可能已经变了。

同时删掉的配置项：`HEALTH_STABLE_WAIT`、`STABLE_SKIP_AGE_HOURS`、`STABLE_INTERVAL`。

**实测影响（要诚实）**：v5 完整流程 239s → v6 209s，但**这 30 秒里绝大部分是网络波动，不是这次改动的功劳**。真实收益是每个被校验的候选省 1 次 HEAD（本次运行 3 个候选，约 3-6s）。

之所以看不出更大效果，是因为 P0 已经让所有 >10h 的老文件跳过探测 —— 而当时被校验的候选全都超过 14 小时。**收益主要体现在健康路径上**：那时第一个候选通常只有 2-4 小时老，探测会真的执行。

### P1 — 用 HEAD 的 `Content-Length` 预筛

**收益：约 -150 秒（31%）｜风险：中（需要安全阀）**

每个候选在读取之前**已经 HEAD 过一次，大小是现成的**（日志里 `(238 MB)` 就是它）。

本次实测的分布：

| 大小区间 | 文件 | 结论 |
|---|---|---|
| 4 - 416 MB | 5 个 | 全部损坏 |
| 875 - 1273 MB | 4 个 | 全部损坏 |
| 1313 - 1418 MB | 历史健康文件 | 健康 |

取 **1000 MB** 阈值可跳过 6 个候选（238/204/4/392/416/904）= 约 152 秒。

**但阈值是经验值，风险真实存在**：如果 NASA 改变分辨率、压缩参数或变量集合，所有文件都会变小，于是**全部被预筛掉，管线永远不发布** —— 而且是静默失败。

**必须配安全阀**，二选一：

- **绝对阈值 + 兜底**：预筛后如果没有任何候选剩下，降级为逐个完整校验并在日志里告警
- **相对阈值（更稳）**：用最近 N 个**已通过门禁**的健康文件大小的中位数 × 0.8 作为阈值，自适应格式变化

推荐相对阈值。代价是要维护一小段"最近健康大小"的状态，但它是唯一不会因格式变化而静默失效的方案。

### P2 — cubemap 向量化

**收益：约 -20 秒（4%）｜风险：低**

`cubemap.py::equirect_to_cubemap` 是 6 面 × 1024² = **630 万次纯 Python 循环**：

```python
for fy in range(face_size):
    for fx in range(face_size):
        dx, dy, dz = face_direction(fi, u, v)          # 含 math.sqrt
        ix, iy = direction_to_equirect(...)            # 含 asin / atan2
        out[fy, fx] = sample_bilinear(...)             # 4 次数组读
```

本机实测 12.6 秒，容器里 25 秒。改成 numpy 预计算方向矩阵 + 批量双线性采样，可降到 1-2 秒。

**输出必须逐字节一致** —— `selftest.py` 正好能验证这一点（现在 6 面都是 `mean 0.000 / max 0`）。

### P3 — 去掉两个调试 PNG

**收益：约 -8 秒（2%）｜风险：极低**

`gcc_source_{ts}.png` 和 `gapfill_{ts}.png` 各约 5 MB，是给人看的调试产物，容器里没人看。用环境变量控制（本地保留，容器关闭）。

### P4 — 避免每次重新下载 StaticSitesClient

**收益：约 -20~30 秒（5%）｜风险：中**

`swa deploy` 每次都要下载那个部署二进制 —— 容器是一次性的，`/root/.swa` 不持久。日志里能看到：

```
Could not find StaticSitesClient local binary
Downloading https://swalocaldeployv2-.../linux/StaticSitesClient@<hash>
```

三个方案：

| 方案 | 说明 | 代价 |
|---|---|---|
| A. 换 Blob 托管 | `publish.py --target blob` 是纯 Python，无二进制 | 失去 SWA 自带 CDN；但 10 个用户无所谓 |
| B. 预热进镜像 | 路径含 hash，CLI 升级即失效 | 脆弱 |
| C. 挂持久卷 | 缓存 `/root/.swa` | 多一个存储资源要管 |

方案 A 最干净，而且镜像能从 696 MB 降到 286 MB。

### P5 — 镜像瘦身

**收益：几秒｜风险：低**

本次镜像已被节点缓存，启动只花了 13 秒。**收益有限，不建议为此单独折腾**，但如果因为 P4 换到 Blob 而顺手去掉 Node，就是白捡的。
